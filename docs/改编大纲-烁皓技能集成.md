# 阶段 00 · 改编大纲 —— shuohao-skills 集成设计说明

## 模式架构：真实引擎优先，浏览器降级

**引擎模式**（`npm run shuohao`，server/shuohaoServer.mjs，127.0.0.1:7791）：

```
前端（StageOutline）
  │  ensureWorkspace → 写 novel.txt / outline.json
  │  runOp('outline_chunk')      → 真实 novel-outline chunk（vol-NN.txt 落盘，前端读回做摘要）
  │  runOp('outline_validate')   → 真实 validate --stage skeleton|full，✓/✗ 原样解析，✗ 详情回炉
  │  runOp('outline_assets')     → 真实 assets 原样 JSON
  │  runOp('outline_render')     → 真实 render --html，报告经 /workspace 静态入口 iframe 打开
  ▼
server/shuohaoServer.mjs（spawn node <skills>/skills/*/scripts/*.mjs，白名单 op → argv，
                           路径 containment，上游产物存在才带 flag，与各技能 USAGE 逐一对齐）
```

* 服务端只做确定性工具编排；创作仍由前端用 BigBanana 自己的模型配置驱动；
* 技能 id 与操作白名单化（前端传不了任意 argv）；workspace 与文件路径严格 containment；
* 校验输出原样透传——包括 `雨戏/人群` 这类关键词扫描门的原文口径文案。

**降级模式**（引擎未启动）：浏览器内移植版（shuohaoGates.ts 的 14 道门 + 本地分卷），
页面横幅明示。两种模式共享同一套创作提示词与回炉循环，只换「裁判」。

## 定位

BigBanana 原有流水线是「rawScript（小说/故事）→ AI 一步拆解成 ScriptData」。问题：
80 万字的小说塞不进上下文；结构（砍谁合谁、爽点怎么排）没有导演拍板环节；
拆解质量全靠模型自觉，没有确定性校验。

[shuohao-skills](https://github.com/eternityspring/shuohao-skills) 的
`novel-outline` 技能正好补这一层：**长文本分卷 → 骨架快版 → 拍板 → 分批分集 →
确定性质量门 → 资产清单代码汇总**。本次改动把这条工作流移植为前端「改编大纲」阶段
（Phase 00），产物再喂给既有流水线。

## 数据流

```
rawScript（小说原文）
  └─ adaptationService.splitVolumes        按章节标题分卷（无章节按字数切，上限 60 卷）
      └─ summarizeVolumes                  逐卷改编向摘要（人物/事件/爽点潜力/可砍支线/高频场景）
          └─ generateSkeleton              骨架快版：改编说明三张表 + 人物分档 + 场景 + 道具 + 爽点表
              └─ shuohaoGates(skeleton)    5 道门（分档上限/场景/道具）→ 未过自动回炉 ≤2 轮
                  └─ 【导演拍板 skeletonApproved】← 流程门：不拍板禁止写分集
                      └─ generateEpisodes  分批 ≤10 集写三栏梗概
                          └─ shuohaoGates(full)  14 道门 → 未过自动回炉 ≤2 轮
                              └─ buildAssetInventory  资产清单（纯代码计算）
                                  └─ composeEpisodeScriptInput  第 N 集 → 结构化剧本任务书
                                      └─ 写入 Episode.rawScript → 既有「剧本与故事」流水线接管
```

数据存放在 `Episode.adaptation`（IndexedDB 随项目自动持久化），结构与
shuohao-skills 的 `outline.json` 字段一一对应（params / adaptation / characters(tier)
/ scenes / props / beats / episodes），方便以后与技能生态互导。

## 质量门口径（services/shuohaoGates.ts）

从 `novel-outline.mjs` 的 `gateReport()` 逐行移植：阈值、判据、失败详情文案、门 id
全部与原仓库一致（id 是日志与下游对账的凭据，保持稳定不动）。

| 门 id | 判据 | 阶段 |
| --- | --- | --- |
| lead-cap / support-cap / functional-cap | 主角组 1–5、配角 ≤10、功能角色 ≤10 | skeleton+ |
| scene-cap | 主场景 ≤ `4+⌈集数/10⌉`（夹 5–15） | skeleton+ |
| prop-cap | 叙事道具 ≤8（无 props 字段明说跳过） | skeleton+ |
| beat-gap | 爽点间隔 ≤3 集且首尾无真空 | beats+ |
| major-early | 最早的 major 不落最后一集 | beats+ |
| once-scene / ep1-hook / ep-fields / crowd-plan / risk-flag / refs / no-dialogue | 一次性场景规避方案、首集钩子、三栏齐全、≥3 人拆解、难点预警、引用完整、叙述体 | full |

阶段即流程门：骨架拍板前只看 skeleton 档；写分集前 beats 档必须过
（间隔与 major 时机错了，分集写完全废）；交付前 full 档全过。

## 与 BigBanana 既有系统的接缝

* **只加不改**：不改 scriptService / StageScript / storageService 的任何既有行为；
  `Episode.stage` 联合类型加了 `'outline'`，Sidebar 顶部新增「阶段 00」入口。
* **应用到剧本** = 把该集骨架+梗概组装成结构化「剧本任务书」写入 `rawScript`
  （targetDuration 按大纲单集时长、清空 scriptData/shots/checkpoint），
  之后的一切生成、一致性、导出全部复用既有能力。
* 生成走 `services/ai/apiCore` 的 `chatCompletion + parseJsonWithRecovery +
  retryOperation`，与剧本服务同一套模型配置与重试口径。

## 已知边界（后续迭代候选）

* 剧本/分镜层的质量门（时长 ±15%、单句 ≤35 字、说话人合法、钩子前 3 拍兑现）
  尚未移植——是下一批工作，放在 ScriptData/Shot 校验处；
* 开场站位（novel-staging 的 blocking → 分镜第一段）与 H3 投产包导出
  （novel-storyboard export）未集成；
* 分卷摘要当前串行执行（稳，不触发限流）；大纲生成模型跟随
  `shotGenerationModel` 的对话模型配置。
